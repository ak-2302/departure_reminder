# 出発リマインダー React + Capacitor 作業計画書

> 現在の実装対象はReact + TypeScript + Vite + Capacitorです。以下の初期段階に残るAndroid表記は、技術変更前の履歴と対応づけるための記録です。以降の実装ではCapacitorとWeb標準の構成を優先します。

## 1. 目的

[仕様書](./仕様書.md)に定義したAndroidアプリを、機能を小さく積み上げながら実装する。各段階では、実装後に動作・品質・設計を確認し、問題を次の段階へ持ち越さないためのリファクタリングを行う。

## 2. 開発方針

- React + TypeScript + Vite + Capacitorを使用する。Android固有の通知・権限・バイブレーションはCapacitorプラグインまたはネイティブブリッジで扱う。
- UI、状態管理、外部API、ローカル保存、通知スケジューリングを分離する。
- 各段階で実行可能な最小機能を作る。
- 検証できない機能を「完了」と扱わない。
- Google APIの実キーや個人情報をGitへ保存しない。
- 既存のユーザー変更を上書きしない。
- 各段階の検証後に、不要な重複・仮実装・責務の混在を整理する。

## 段階2：ローカル設定と出発時刻計算

### 実装

- 出発地点、移動手段、準備時間、余裕時間、通知設定をDataStoreまたはRoomへ保存する。
- 予定、経路、計算結果のドメインモデルを定義する。
- `出発時刻 = 予定開始時刻 - 移動時間 - 準備時間 - 余裕時間` を実装する。
- 仮の予定と移動時間から、ホーム画面に計算結果を表示する。

### 完了確認

- 設定を保存してアプリを再起動しても復元できる。
- 日付境界、タイムゾーン、過去の予定、出発時刻が現在時刻に近い場合を正しく扱う。
- 予定開始時刻と出発時刻の内訳が画面で一致する。

### リファクタリング

- 計算処理をUIとRepositoryから分離し、純粋関数または独立サービスにする。
- 時刻を端末時刻へ直接依存させず、テスト可能なClockを使う。
- 文字列としての日時と内部の日時型を混在させない。
- 設定値の範囲チェックとデフォルト値を一か所にまとめる。

### 次段階へ進む条件

- 計算ロジックの単体テストが成功する。
- 仕様書の計算式と実装結果をテストケースで照合できる。

## 段階3：Google認証・Calendar API

### 実装

- Googleアカウント認証を追加する。
- `calendar.events.readonly` の最小スコープで予定を取得する。
- 対象期間、繰り返し予定、キャンセル予定、終日予定、場所なし予定を処理する。
- ページングと差分同期を実装する。
- 取得結果をローカルに保存し、ホーム画面へ表示する。

### 現在の実装状況（2026-10-24）

- Google Identity Servicesを使うWeb側のOAuth・Calendar APIアダプターを追加した。
- OAuthクライアントIDを`.env.local`の`VITE_GOOGLE_CLIENT_ID`から読む。
- 予定取得は今後7日、最大50件、繰り返し予定を展開し、終日・キャンセル・場所なし予定を除外する。
- `nextPageToken`を使ったページングを追加し、最大10ページまで予定を取得する。
- 経路更新日時を予定へ保存し、経路未取得の予定には通知を設定しないようにした。
- カレンダー再取得で消えた予定について、対応するローカル通知を取り消す処理を追加した。
- Routes APIは条件ごとに10分間結果をキャッシュし、同時実行中の同一条件リクエストも共有する。
- 公共交通機関では予定の`startAt`を出発時刻としてRoutes APIへ渡し、キャッシュキーにも含める。
- 通知設定済みの予定は、経路更新時に新しい出発時刻で通知を再設定する。開始時刻が変更された予定は通知設定を解除し、再計算を要求する。
- 通知タップ時は通知IDから対象予定を特定し、アプリ内で対象予定を先頭に表示する。
- 通知タップ時と「予定の詳細」操作で、予定・出発時刻・経路・通知状態を確認できる詳細モーダルを表示する。
- 予定詳細からGoogle Maps Directions URLを開き、出発地点・目的地・移動手段を渡す。
- 設定画面を開いた時に通知権限を確認し、許可・拒否・未確認の状態を表示する。
- 通知権限が拒否されている場合、Androidアプリの通知設定を開く導線を表示する。
- Capacitor AndroidのWebView上でのOAuth互換性と、実Googleアカウントを使う結合試験は未完了。必要に応じてネイティブOAuthブリッジへ切り替える。
- Android版はCapacitor Browser、Authorization Code + PKCE、HTTPS App Linkで認証する実装へ変更した。GoogleのAndroid OAuthではカスタムURIスキームを使用せず、`https://ak-2302.github.io/departure_reminder/oauth2redirect`を使う。実端末でのGoogle Cloud設定済み結合試験は未完了。

### 完了確認

- 許可、拒否、キャンセル、再認証の各フローが成立する。
- 実際のテスト用Googleカレンダーの予定が表示される。
- 繰り返し予定が個別発生予定として表示される。
- 場所なし・終日・キャンセル予定が仕様どおりに扱われる。
- ページングを含む予定取得が欠落なく完了する。

### リファクタリング

- OAuth、Calendar API通信、予定変換、ローカル保存を別の責務に分ける。
- APIレスポンスをUIモデルへ直接渡さない。
- トークンや予定の詳細をログ出力しない。
- API呼び出しの再試行・タイムアウト・キャンセルを共通化する。

### 次段階へ進む条件

- 認証と予定取得の結合テストが成功する。
- 認証情報を含まないテストログで問題を追跡できる。

## 段階4：目的地・Routes API

### 実装

- 予定の場所文字列を目的地として解決する。
- 曖昧な場所、不正な場所、解決失敗を扱う。
- 徒歩、自転車、自動車、公共交通機関の移動手段を実装する。
- 予定開始時刻を考慮した経路取得を実装する。
- 移動時間と取得時刻を保存し、出発時刻を再計算する。
- 必要に応じてGoogle Mapsアプリへ経路を引き渡す。

### 完了確認

- 実在するテスト住所について、選択した移動手段の所要時間を表示できる。
- 公共交通機関で出発・到着時刻の扱いが正しい。
- 取得失敗時に誤った出発時刻を通知しない。
- 経路取得日時を画面で確認できる。
- APIキーの制限と日次クォータが設定されている。

### 現在の実装状況（2026-10-24）

- `src/googleRoutes.ts`にRoutes API呼び出しを分離し、出発地点・目的地・移動手段から所要時間（分）を取得する境界を追加した。
- ホーム画面の「移動時間を更新」から取得処理を実行でき、キー未設定や経路なしをステータス表示する。
- Google CloudのAPIキー制限、実住所での実API検証、公共交通機関の出発時刻考慮、結果キャッシュは未完了。

### リファクタリング

- 目的地解決、経路計算、計算結果の保存を分離する。
- Routes APIのレスポンス全体を保存せず、必要最小限の結果だけ保存する。
- 同じ条件の経路を短時間に重複取得しないキャッシュを追加する。
- APIの移動手段名を画面文言へ直接埋め込まない。

### 次段階へ進む条件

- 実APIを使った主要移動手段の検証が成功する。

### 次段階へ進む条件

## 段階6：予定変更・同期・復元

### 実装

- 定期同期と手動更新を追加する。
- 予定の作成、変更、削除、キャンセルを検知する。
- 変更時に経路と通知を再計算する。
- 端末再起動後に未来の通知を復元する。
- タイムゾーン・端末時刻変更時に再計算する。

### 完了確認

- Googleカレンダー側で予定を変更するとアプリの表示が更新される。
- 予定削除・キャンセル時に通知が残らない。
- 端末再起動後に未来の通知が復元される。
- オフライン復帰後に同期が再開される。
- 同期の多重実行でデータや通知が重複しない。

### 現在の実装状況（2026-10-24）

- 取得済みの予定と経路更新結果をCapacitor Preferencesへ保存し、次回起動時に復元する処理を追加した。
- OAuthトークンは保存していないため、定期的なバックグラウンド再同期と認証更新は未完了。
- アプリ復帰時とネットワーク復旧時は、アプリ起動中に保持しているアクセストークンがある場合だけ自動再同期する。
- 端末再起動後の通知復元、タイムゾーン変更、端末時刻変更は実機で未検証。

### リファクタリング

- 同期処理を冪等にする。
- 同期状態、経路状態、通知状態を別々に管理する。
- 失敗した同期を無限リトライしないよう制限する。
- Roomのマイグレーション方針を定める。

### 次段階へ進む条件

- 予定変更・削除・再起動の結合テストが成功する。
